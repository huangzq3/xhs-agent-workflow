# 定时发布

定时发布是“延后发生的外部状态变更”，不能只保存一个时间字段。发布前确认必须同时绑定内容版本、目标账号、定时时间、明确时区、最晚允许执行时间和执行方式。

## 三种执行方式

按当前环境实际可用能力选择，不绑定 TRAE、WorkBuddy、豆包、Codex、Claude Code 或其他产品名称。

| 方式 | 可选择的证据 | 执行要求 |
|---|---|---|
| 平台原生定时发布 | 已登录的平台操作能力明确展示定时发布入口，并能返回排期记录或其他可核对凭据 | 获得发布前确认后提交排期并保存凭据；到点后核对是否真正上线 |
| 运行工具到点唤醒 | 当前运行环境明确提供一次性定时任务、自动唤醒或等价能力，能力快照记录为可用 | 到点后重新检查账号、内容版本和发布规则，处于允许时间窗口内才执行一次 |
| 人工到点交接 | 前两种能力不可用或账号负责人主动选择人工操作 | 生成中文 HTML 交接页和提醒；只有账号负责人确认实际操作后才记录结果 |

能力未知不等于可用。运行工具只支持提醒、不支持无人值守执行时，应归入“人工到点交接”。

## 时间窗口

- 定时时间必须包含时区，不接受没有时区的日期时间。
- 同时由账号负责人明确“最晚允许执行时间”。
- 运行工具到点唤醒或人工到点交接只能在这两个时间之间开始发布。
- 超过最晚允许执行时间后标记“已错过允许执行时间”，停止自动补发，重新选择时间并完成新的发布前确认。
- 修改定时时间、最晚执行时间、执行方式、账号、内容或素材后，旧的发布前确认失效。

## 到点执行

平台原生定时发布在提交排期时消费一次发布前确认，并保存平台排期凭据。平台到点是否真正上线仍需核对。

运行工具到点唤醒或人工到点交接在定时时间到达后执行以下复核：

1. 目标账号仍一致；
2. 内容、素材顺序和校验指纹未变化；
3. 账号运营策略版本仍有效；
4. 重新运行发布规则检查，结果仍为“符合当前规则”；
5. 当前时间尚未超过最晚允许执行时间。

任何一项不满足时停止，并用中文说明需要账号负责人重新决定的事项。

## 上线结果

以下时间必须分开记录：

- 定时时间：希望内容上线的时间；
- 排期提交时间：向平台提交定时任务的时间；
- 执行开始时间：运行工具或账号负责人开始发布的时间；
- 实际上线时间：平台内容真正变为可访问状态的时间。

只有最后一项可以作为内容复盘的起点。核对依据可以是平台元数据、已经上线的远端页面或账号负责人的人工确认。只看到“排期成功”“提交完成”或本地任务已运行时，不得填写实际上线时间。

## 内部命令

内部执行器可使用：

```bash
python3 workflow_cli.py set-schedule publication.json \
  --scheduled-at 2026-08-20T20:00:00+08:00 \
  --expires-at 2026-08-20T20:30:00+08:00 \
  --method agent_wakeup --actor operator

python3 workflow_cli.py scheduled-due --root /path/to/workspace
```

命令输出属于机器层，不得直接粘贴给账号负责人；人工审阅仍使用中文 HTML。
